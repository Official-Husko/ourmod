The hook logic is actually pretty clear. Async is using [rax+0xC4] == 0x40C00000 as the discriminator for the player object. 0x40C00000 is the float bit-pattern for 6.0.

Conceptually it does:

if (*(uint32_t *)(rax + 0xC4) == 0x40C00000) {
    saved1 = *(uint64_t *)(rax + 0x60);
    saved2 = *(uint64_t *)(rax + 0x64);
    saved3 = *(uint64_t *)(rax + 0x68);
}

*(uint64_t *)(rax + 0x60) = saved1;
*(uint64_t *)(rax + 0x64) = saved2;
*(uint64_t *)(rax + 0x68) = saved3;

So when the current object is the player, it records the player's position-like data. For the other objects passing through this code, it overwrites those fields with the saved player values — hence vehicles/NPCs getting pulled to you.

One correction to the extractor output

These pairs:

body+0x18 -> cave+0x1f4 size=8
body+0x19 -> cave+0x1f4 size=4

aren't two actual instructions.

The second one is a false positive from our lightweight decoder scanning inside the preceding x86 instruction.

For example the real instruction is:

48 89 1D D5 01 00 00
mov qword ptr [rip+0x1d5], rbx

but the scanner starts again at its second byte:

89 1D ...

and incorrectly recognizes that as a separate 32-bit RIP-relative store.

Same thing happens for the other pairs.

So the actual data sizes really are:

+0x1F4 : 8 bytes
+0x258 : 8 bytes
+0x2BC : 8 bytes

which the generated YAML fortunately already chose correctly.

into the integer correctly.

2. Calculate the required cave size

Don't assume that:

body length + return jump

is the complete cave anymore.

For this hook:

body        ends at 0x64
return jump occupies 0x64..0x71
data exists through 0x2c3

So calculate the highest referenced byte:

func requiredCaveSize(bodyLen int, data []HookDataConfig) uintptr {
	used := uintptr(bodyLen + 14)

	for _, d := range data {
		end := uintptr(d.Offset) + uintptr(d.Size)
		if end > used {
			used = end
		}
	}

	const page = uintptr(0x1000)

	return (used + page - 1) &^ (page - 1)
}

For this feature that returns:

0x1000

which matches what Async allocated.

4. Initialize the cave data

Generic helper:

for _, d := range hook.Data {
	buf, err := parseHexBytes(d.Bytes)
	if err != nil {
		return fmt.Errorf(
			"data at offset %#x: %w",
			d.Offset,
			err,
		)
	}

	if d.Size != 0 && len(buf) != d.Size {
		return fmt.Errorf(
			"data at offset %#x: configured size %d, got %d bytes",
			d.Offset,
			d.Size,
			len(buf),
		)
	}

	addr := cave + uintptr(d.Offset)

	if err := writeMemory(pid, addr, buf); err != nil {
		return fmt.Errorf(
			"write cave data at %#x: %w",
			d.Offset,
			err,
		)
	}
}

Technically these explicit zero writes aren't necessary because Linux anonymous mmap gives you zeroed memory. But keeping them is useful because the YAML now describes the full layout.

5. This part is critical: keep the cave writable

Your earlier PoC did approximately:

remoteMprotect(
	pid,
	cave,
	caveSize,
	unix.PROT_READ|unix.PROT_EXEC,
)

That is fine for Immortality.

It is not fine for this teleport hook.

Change it to:

prot := unix.PROT_READ | unix.PROT_EXEC

if hook.Writable {
	prot |= unix.PROT_WRITE
}

if err := remoteMprotect(
	pid,
	cave,
	caveSize,
	prot,
); err != nil {
	return err
}

For this YAML:

writable: true

you end up with:

PROT_READ | PROT_WRITE | PROT_EXEC

for the cave.

That allows these instructions to work:

mov qword ptr [cave+0x1f4], rbx
mov qword ptr [cave+0x258], rbx
mov qword ptr [cave+0x2bc], rbx

Without write permission, the hook can crash the game.

This same observation also matters for Player Speed, because that hook contains:

mov dword ptr [cave+0xc8], 0x419bf3b6

so Player Speed should likely have:

writable: true

too.
